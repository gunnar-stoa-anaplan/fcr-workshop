The 6-step FCR delivery approach and what to do (and not do) on a first engagement

🚨 First Implementation Warning

Work with Anaplan Professional Services on your first FCR engagement. This is not optional advice — it is the difference between a 4–6 week clean delivery and a 6-month struggle. FCR's consolidation rule setup, account tagging, and intercompany configuration are where implementations go wrong without experienced guidance. The Anaplan Professional Services team is available for scope discussions and approach planning at no charge during the sales cycle.

The 6-Step FCR Delivery Approach

1

Discovery & Requirements

The most important phase. Deliverables:

  • Requirements workbook completed — entity hierarchy, chart of accounts, consolidation methods, currency setup
  • Tenant type decision locked: 10-dimension (AMER/UK/Nordics), 11-dimension with Group (Europe), or 14-dimension IFRS accelerator
  • Group dimension decision documented and signed off — this cannot be changed after provisioning
  • Data source mapping: which GL systems feed which entities, which require account mapping
  • Historical data approach decided: load raw and let FCR consolidate, or load pre-consolidated data
  • Business Requirements Document (BRD) drafted and presented back to customer
2

Configuration

Build the FCR tenant based on confirmed requirements:

  • Provision tenant (3–5 day lead time once all information is submitted)
  • Import dimensions: entity hierarchy, account dimension, custom dimensions
  • Configure ownership structure and consolidation methods
  • Set up consolidation rules: ARAP elimination, NCI, equity method, proportional method
  • Configure currency dimension and conversion parameters
  • Enable journals (feature flag + security setup)
  • Build integration: staging tables, member mappings, import definitions
3

Data Load

Load source data and validate the results:

  • Open required periods
  • Run initial data load via staging tables and import definitions
  • Verify data loaded correctly — check entity counts, period totals, currency split
  • Two approaches for historical data: (a) load raw trial balances and let FCR consolidate; (b) load pre-consolidated data directly
  • Note: approach (a) is preferred for ongoing periods; approach (b) may be faster for historical setup
4

Reconciliation & Validation

Verify that FCR's output matches the prior system:

  • Run currency conversion and consolidation
  • Compare consolidated P&L and balance sheet to prior system output
  • Investigate and resolve differences — common causes: consolidation rule gaps, account tagging errors, missing intercompany data
  • Run validation reports: Validations Open Period and Movement Validations
  • Document any known differences and get customer sign-off
5

User Acceptance Testing (UAT)

Customer-led validation of the configured system:

  • Finance team runs UAT in the configured tenant
  • Test all consolidation methods, journal entry, intercompany matching
  • Test period initialization for a new period end-to-end
  • User training: finance team, controllers, system administrators
  • Sign-off on UAT results before proceeding to cutover
6

Cutover

Go-live with production data:

  • Parallel run strongly recommended — run both old and new systems simultaneously for at least one period before decommissioning the prior system
  • Final data load with sign-off balances
  • Production security configuration: user roles, data access, folder permissions
  • Handover documentation: configuration guide, admin procedures, period-end checklist
  • Hypercare period: Anaplan Professional Services on standby for first 1–2 live close cycles

Where Implementations Go Wrong

Based on experience across multiple FCR implementations, three areas account for the majority of project delays and escalations:

⚠ Failure Area 1: Consolidation Rule Setup

FCR's tag-based consolidation rules are unlike any other consolidation system. Rules reference account tags — not hardcoded account IDs. A mistyped tag silently fails to fire. Missing rules result in incomplete eliminations that don't produce errors, just wrong numbers. Without guidance from someone who has done this before, it's easy to have a system that looks correct until you check the intercompany elimination detail.

⚠ Failure Area 2: Account Dimension Configuration

The account dimension carries more configuration than any other dimension in FCR: tags, classification, operator, P_conversion, consolidation rule assignment, movement classification. Getting accounts wrong — especially tags — creates compounding errors across conversion, elimination, and cash flow. Get the account dimension fully configured and validated before loading any data.

⚠ Failure Area 3: Different Approach, Same Experience

Consultants with experience in HFM, OneStream, or Cognos Controller often assume FCR works the same way. It doesn't. FCR's approach to eliminations, its DataView dimension concept, and its tag-based rules are genuinely different. Experience with other consolidation tools is valuable context — but it is not a substitute for understanding FCR's specific mechanisms. Approach it as a new tool, not a familiar one with different buttons.

Historical Data Load: Two Approaches

Approach A — Load Raw, Let FCR Consolidate

  • Load each entity's trial balance as-is from source GL
  • FCR runs consolidation: currency conversion, eliminations, NCI
  • Preferred for ongoing operations
  • Takes longer to set up correctly — all rules must be complete before this works
  • Produces a clean audit trail of what came from the GL vs. what was calculated

Approach B — Load Pre-Consolidated Data

  • Load already-consolidated historical data directly
  • FCR does not re-consolidate this data — it is loaded as-is
  • Faster for historical periods during cutover
  • Less useful for investigation and audit — no intercompany detail in the system
  • Not appropriate for live ongoing periods

Provisioning Timeline

FCR tenant provisioning takes approximately 3–5 days once all required information is submitted. The provisioning request is generated in Salesforce after deal close, but requires Customer Success, the AE, and the partner to align on tenant type before it can be actioned.

🚨 Irreversible Decision

The tenant type — 10-dimension, 11-dimension with Group, or 14-dimension IFRS accelerator — cannot be changed after provisioning. Choosing the wrong type means starting over from scratch. This decision must be made with the customer before any provisioning request is submitted.
